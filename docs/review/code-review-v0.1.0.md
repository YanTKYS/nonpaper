# NonPaper v0.1.0 コードレビュー結果

## レビュー概要

- 対象: コミット `27706fc`（`NonPaper v0.1.0`）
- 観点: データ整合性、並行実行、安全なファイル操作、API の状態遷移、テスト容易性
- 実施した確認: サーバー実装、ブラウザー側 JavaScript、既存単体テスト、設定および設計文書の静的レビュー
- 結論: **要修正**。特にイベント単位の read-modify-write が排他されていないため、同時操作で正常終了した更新が失われる問題をリリース前に解消する必要がある。

## 指摘事項

### [高] 1. read-modify-write 全体が排他されず、同時更新が失われる

**該当箇所:** `src/NonPaper/Program.cs:28-34`、`src/NonPaper/Services/EventRepository.cs:27-55`

`SaveAsync` のセマフォが保護するのは JSON ファイルへの書き込みだけであり、`GetAsync` からオブジェクト変更、`SaveAsync` までの一連の処理は保護されていない。たとえば二つの資料名変更が同時に同じ `event.json` を読み、それぞれ別の資料を変更して保存すると、後から保存したスナップショットが先の変更を上書きする。状態変更、アップロード、並び替え、削除の組み合わせでも同じ問題が発生する。両 API は成功を返し得るため、利用者はデータ消失を検知できない。

既存の `ConcurrentSafeUpdates_AlwaysLeaveValidJson` は「JSON が壊れない」ことだけを確認し、全更新が反映されたかは確認していない（`tests/NonPaper.Tests/EventRepositoryTests.cs:22-27`）。そのため現状のテストはこの競合を見逃す。

**推奨対応:** リポジトリにイベント単位の更新 API（例: `UpdateAsync(id, Func<EventRecord, ...>)`）を設け、読み込み・検証・変更・原子的保存を同じロック内で実行する。楽観的同時実行制御を採用する場合は revision/ETag を保存し、競合時に `409 Conflict` を返す。異なるフィールドを並行更新する統合テストに加え、削除と更新の競合テストを追加する。

### [高] 2. 複数 PDF のアップロードが非トランザクショナルで、孤立ファイルを残す

**該当箇所:** `src/NonPaper/Program.cs:29`

アップロード処理は各ファイルを検証した直後に最終保存先へ書き込み、全ファイルの処理後に一度だけイベント JSON を保存する。このため、先頭が正常な PDF、2 件目が不正なファイルであれば、API は 400 を返す一方、先頭 PDF はディスクに残り、JSON には登録されない。コピー中の切断・キャンセル、ディスク容量不足、最後の `SaveAsync` 失敗でも同様である。孤立ファイルは画面や API から削除できず、保存領域を消費し続ける。

また、同時アップロードが同じ古い資料一覧を基に成功すると、指摘 1 により一方のメタデータだけが失われ、その PDF も孤立する。

**推奨対応:** 最初に全ファイルの件数、サイズ、拡張子、シグネチャを検証し、イベント専用の一時領域へ保存する。JSON 更新まで成功した場合だけ最終名へ移動し、失敗時は `finally` で今回作成した一時ファイルおよび最終ファイルを削除する。ファイル確定とメタデータ更新も指摘 1 のイベントロック内で扱い、途中失敗およびキャンセル時に残骸がないことをテストする。

### [高] 3. 削除と更新の競合により、削除済みイベントが部分的に復活し得る

**該当箇所:** `src/NonPaper/Program.cs:28-34`、`src/NonPaper/Services/EventRepository.cs:36-64`

各変更 API は認証時にイベントを読み込んだ後、削除処理とは独立して変更・保存する。更新要求が認証を済ませた直後に削除要求がディレクトリを消すと、更新側の `SaveAsync` はディレクトリを再作成して古いイベントを保存できる。反対の順序では、成功応答済みの更新が削除される。資料アップロードが絡むと JSON のみ、または PDF のみが再生成される可能性もある。

さらに `DeleteAsync` は待機中の処理があり得るセマフォを解放した直後に `Locks` から取り除く。古いセマフォの待機者と、新しく辞書へ追加された別セマフォの利用者が同一イベントを同時に操作できるため、「イベント別ロック」という前提自体が崩れる。

**推奨対応:** 認証後の再読込、`deleting` への遷移、削除までを同じイベント単位の排他区間で行う。更新 API は排他区間内で最新状態を再確認し、`deleting` または削除済みなら保存せず `404`/`409` を返す。ロックエントリは安全な参照カウント方式で管理するか、少なくとも待機者が存在し得る状態で辞書から削除しない。削除と状態変更・名称変更・アップロードを同期させる競合テストを追加する。

### [中] 4. 資料の変更 API が下書き限定というサーバー側ルールを一貫して適用していない

**該当箇所:** `src/NonPaper/Program.cs:29-32`

新規アップロードだけは `Status != "draft"` を `409` で拒否するが、名称変更、並び替え、資料削除には同じ検査がない。そのため公開中の参加者が閲覧している最中でも管理 API から資料名・順序・実体を変更できる。特に削除では、参加者が一覧を取得してから PDF を要求するまでの間に 404 となる。画面上で操作を見せるかどうかに関係なく、Bearer トークンを持つクライアントは API を直接呼び出せるため、制約はサーバーで統一する必要がある。

**推奨対応:** 資料に対する作成・更新・並び替え・削除の全 API で、共通の状態検証を行う。公開中の編集を仕様として許可するなら、アップロードだけを禁止する不整合を解消し、参加者側の一覧と PDF 取得間の競合に対する仕様・エラー表示を明文化する。

### [中] 5. イベント JSON の破損を検証・診断する経路がない

**該当箇所:** `src/NonPaper/Services/EventService.cs:14-18`、`src/NonPaper/Services/EventRepository.cs:27-34`

`TokenMatches` は保存済みの `ManagementTokenHash` が null、不正長、非 16 進文字の場合に `Convert.FromHexString` から例外を送出する。`GetAsync` も不完全・破損 JSON の逆シリアル化例外をそのまま伝播する。一方 `Auth` が業務エラーへ変換するのは `ArgumentException`、`KeyNotFoundException`、`UnauthorizedAccessException` だけであり、開発環境では詳細例外が露出し、運用環境では一律エラーとなる。手動復元や書込み障害後に、どのイベントが破損したかを識別できる構造化ログもない。

**推奨対応:** 永続モデルの読み込み時に必須項目、ハッシュ長・形式、状態値、資料 ID を検証し、専用のデータ破損例外へ変換する。イベント ID とともにエラーを記録し、クライアントには詳細を含まない 500 を返す。破損 JSON、不正ハッシュ、欠落プロパティを使ったテストを追加する。

## テストに関する総評

現在のテストはリポジトリの基本保存、パストラバーサル対策、ディレクトリ削除、トークン比較に限定されている。HTTP API の認証・状態制約、複数ファイルの途中失敗、同時更新、削除競合を検証する `WebApplicationFactory<Program>` ベースの統合テストを優先して追加すべきである。特に「レスポンスが成功した全操作の結果が最終状態に残ること」と「失敗後に JSON 未登録の PDF が存在しないこと」を、単なる JSON 構文妥当性より強い不変条件として確認することを推奨する。

## 判定

指摘 1〜3 は、通常の複数ブラウザー操作でもデータ消失・孤立データ・削除済みデータの復活につながるため、v0.1.0 のリリースブロッカーと判断する。修正後に競合とロールバックの統合テストを追加し、再レビューを実施すること。
